# 远程协助通道的本地复现

> 分析对象：管理端的远程协助子系统（推送触发 → 协助服务 → REST 轮询 → 命令执行）。
> 证据等级：A（代码）+ C（现场复现）。
> 配套阅读：[[10-remote-assist]]（静态分析）、[[research/push-channel-reverse]]（推送帧）、[[research/unlocker-architecture]]（工程实现）。

## 一、结论速览

| 问题 | 答案 |
| --- | --- |
| 协助是怎么被触发的 | 推送一条 `subMsgType = assist-notify` 的消息 |
| 设备端怎么拿指令 | 每约 8 秒 **轮询** `GET /assists/{aid}/tasks`，不是长连接推送 |
| 有几种指令 | 14 种，从执行命令到装卸应用、读写文件系统 |
| 能执行任意 shell 吗 | 能，`executeCmd` 直接走 `Runtime.exec` |
| 复现难在哪 | 不在协议，而在 TLS 与 Host 还原 |
| 为什么要反向代理 | 客户端只认固定 IP，且做 `matchIp` 校验，不走 DNS |
| 复现成功的判据 | 设备在控制台里回显 `READY` 与命令输出 |

一句话概括：**这不是漏洞，是功能——一条设计上就存在、权限上完全合理、只是把执行权交给了远端的通道。**

---

## 二、为什么能完整复现

四个条件同时成立，缺一不可：

| 条件 | 说明 |
| --- | --- |
| 客户端不做证书固定到具体公钥 | 只走系统信任链，因此代理一个「系统信任」的证书即可 |
| 寻址用裸 IP | 反向代理可以绑定该 IP 接管 |
| 指令是明文 JSON | 无二次加密，拿到响应即可读 |
| 轮询而非推送 | 不需要维持长连接，只需按节奏应答 |

反过来说：只要有一条不成立，整条链路就断。**这也是判断「这套方案是否可靠」的最快方式——看它依赖了几个假设。**

## 三、拓扑

```text
[设备] --443/TLS--> [本地反向代理 :443] --SNI 还原--> [真实服务器]
                          |
                          +-- 拦截 /api/v1/assists/* --> 本地应答
```

| 角色 | 地址 |
| --- | --- |
| 设备 | 热点内的 `.130` |
| 网关/代理 | 热点网关 `.1` |
| 上游真实服务器 | 三个 IP，按响应里下发的地址选择 |

关键点：反向代理模式下，插件看到的 Host 是**上游 IP**，而不是原始域名。必须从 `flow.client_conn.sni` 取回真实域名，否则所有针对域名的路由判断都会失效。这是第一个必踩的坑。

## 四、四个 REST 接口

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| `GET` | `/api/v1/users/{uid}/devices/{did}/assists` | 查询该设备待处理的协助会话 |
| `GET` | `/api/v1/assists/{aid}/tasks` | 拉取该会话的任务列表（轮询） |
| `PUT` | `/api/v1/assists/{aid}/active` | 置会话为活跃/结束 |
| `POST` | `/api/v1/assists/{aid}/result` | 上报任务执行结果 |

### 4.1 信封格式

所有响应都套一层信封：

```json
{ "code": 200, "message": "ok", "httpResponse": <真正的负载> }
```

**注意**：`httpResponse` 是字符串化的 JSON，不是嵌套对象。客户端会做二次解析。

### 4.2 任务形状

```json
{ "id": 12345, "instruction": "executeCmd(\"id\")", "step": 1 }
```

`instruction` 是「方法名(参数)」形式的字符串，参数为 JSON 或字符串字面量。

### 4.3 一个致命细节

在另一处同类改造中（动态码伪造），响应**不能**包含 `httpResponse` 键——因为那个接口的正常响应体是裸的，多一层包装会让客户端解析失败。同一个体系里两种信封并存，是排查故障时最常见的误判来源。

## 五、能力清单

| 能力 | 说明 |
| --- | --- |
| `executeCmd` | 执行 shell 命令，返回 stdout/stderr |
| `downloadFile` | 从指定 URL 下载到设备路径 |
| `uploadFile` | 从设备路径上传到服务器 |
| `installAppOffline` | 用本地路径安装 APK |
| `installAppOnline` | 从 URL 下载后安装 |
| `unInstallApp` | 卸载应用 |
| `getInstallAppList` | 列出已安装应用 |
| `getAppInfo` | 单个应用详情 |
| `getFileTree` | 列目录 |
| `renameFile` | 重命名/移动 |
| `clearAppData` | 清应用数据 |
| `clearFirewall` | 清防火墙规则 |
| `getSystemConfig` | 读系统配置 |
| `dumpAppUsageEvents` | 导出使用记录 |
| `exit` | 结束会话 |

这 14 项合起来等价于「一个完整的远程管理 shell」。值得注意的是 `clearAppData` 与 `clearFirewall` 同时存在——前者能清掉应用的本地状态，后者能解除网络限制。

## 六、复现步骤（概览）

### 6.1 前置

| 项 | 要求 |
| --- | --- |
| 代理工具 | 支持反向模式与 Python 插件 |
| 证书 | 需被目标设备信任（或走应用自身不校验的路径） |
| hosts / IP 接管 | 让目标域名或 IP 指向代理 |
| 控制端口 | 一个本地端口用于人工投喂指令 |

### 6.2 插件里的四个钩子

| 钩子 | 职责 |
| --- | --- |
| 协助主逻辑 | 拦截四个接口，维护会话与任务队列 |
| 动态码伪造 | 让客户端的取码请求拿到指定值 |
| 关于页载荷 | 替换「关于」页的下发内容 |
| 真实上游 | 除被拦截路径外，其余全部透传到真实服务器 |

第四个钩子是整套方案能用的关键：只拦需要拦的，其余照常放行，这样客户端的其他业务不会崩。

### 6.3 Hosts 清单

需要把管理端相关的域名全部指向代理：平台、微服务、响应、控制、管理、课件服务、云资源、播放、任务奖励等，共十余条。

**一个必须避开的项**：不要劫持系统的连通性检测域名。把它指向本地会让系统判定「无网络」，从而触发一堆与本研究无关的降级行为。

### 6.4 控制台

复现期间通过命令行投喂指令，主要命令：

| 命令 | 作用 |
| --- | --- |
| `!status` | 查看当前会话状态 |
| `!new <id>` | 新建协助会话 |
| `!hist [n]` | 查看历史任务 |
| `!call` | 手动触发一次任务拉取 |
| `!queue` | 查看待发任务队列 |
| `!raw` / `!b64` | 以原始/Base64 形式查看负载 |
| `!cd` / `!wait` | 切换目录 / 等待 |

### 6.5 验证

设备端表现为：约 8 秒后拉取到任务，回显执行结果。判据是**控制台看到命令输出**，而不是「设备看起来正常」。

## 七、两类坑

### 7.1 会让进程直接崩的

「关于页载荷」这类改造如果在解析 URL 时抛未捕获异常，会触发客户端的崩溃计数机制——累计三次即进入安全模式页。表现为「设备忽然跳到一个不认识的界面且退不出来」。

排查方式：先只启用最小钩子（协助主逻辑 + 真实上游），确认链路通，再逐个加其余钩子。

### 7.2 会让命令看起来「没执行」的

| 现象 | 原因 |
| --- | --- |
| 任务拉到但不执行 | `instruction` 语法不合法，客户端解析失败后静默丢弃 |
| 执行了但没结果 | 结果上报接口被拦但应答格式不对，客户端判定失败后重试 |
| 一切正常但设备重启后失效 | 复现依赖运行时注入，重启即丢 |

## 八、关闭与恢复

复现结束后需要恢复的顺序：

1. 撤销 hosts / IP 接管；
2. 停掉代理进程；
3. 重启管理端应用（清运行时的钩子状态）；
4. 确认设备能重新连上真实服务器。

**顺序很重要**：先撤接管再停进程，否则进程退出时可能留下半开的连接状态。

## 九、边界

| 项 | 说明 |
| --- | --- |
| 需要设备信任的证书 | 这是复现的前提，不是可以绕过的环节 |
| 依赖轮询节奏 | 客户端轮询间隔固定，无法加速 |
| 不改变服务端状态 | 全程只伪造本地应答，真实服务端不知情 |
| 不具备持久性 | 重启即失效，无自启动 |
| 一次会话一个 ID | 会话 ID 必须新鲜，复用会撞上服务端状态 |

## 十、这条通道说明了什么

把这条链路和 [[research/attack-chain]] 里那条对比，会发现一个有意思的并列：

| | 协助通道 | 端到端链路 |
| --- | --- | --- |
| 设计意图 | 就是给人远程操作设备 | 无 |
| 需要破解 | 只需接管 TLS 信任 | 需要劫持长连接、伪造帧、构造载荷 |
| 能力 | 14 种指令，含任意命令 | 完整代码执行 |
| 持久性 | 无 | 有 |

**结论：这条通道的能力几乎不逊于那条费尽力气打通的链路，而它本来就在那里。** 这不是在说「设计错了」，而是在说：一个以「方便管理」为目标的能力，其默认可达范围通常远超用户的预期。

一句话概括：**最危险的后门不是藏起来的那个，而是被写在说明书里的那个。**
