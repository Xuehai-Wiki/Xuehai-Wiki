# 日志与埋点的上传端点全谱

> 分析对象：管理端及其关联应用的日志生产与上报链路（15 个 APK 的审计结果）。
> 证据等级：A（反编译代码 + 端点常量）。
> 配套阅读：[[05-logging]]（日志体系全貌）、[[research/envspoof]]（伪装模块）、[[research/login-chain-audit]]（登录链路审计）。

## 一、结论速览

| 问题 | 答案 |
| --- | --- |
| 有几组自有上传接口 | 4 组：日志归档、行为埋点、定时任务、文件服务器 |
| 有几家第三方 SDK | 7 家，覆盖崩溃、性能、埋点、语音、推送 |
| 日志存在哪 | 应用私有目录与外部存储的固定路径，文件名带包名与进程号 |
| 抓的是什么 | `logcat` 按进程过滤 + 应用内自建 LogManager |
| 关掉应该改哪层 | **方法 hook 优先**，域名黑名单只能兜底 |
| 最不该做的 | 全局封禁文件服务器域名 |
| 为什么 | 它同时承载头像、作业附件等正常业务，封了会大面积功能失效 |

一句话概括：**这套体系的日志是四条自有管道加七条第三方管道并行，任何单点拦截都只是让某几条断掉，而不是「关掉了日志」。**

## 二、四组自有接口

| # | 用途 | 方法 | 路径 |
| --- | --- | --- | --- |
| 1 | 日志归档 | `POST` | `/api/v3/users/{userId}/devices/{deviceId}/logs` |
| 2 | 行为埋点 | `POST` | `/api/v1/userTrackDataReceiver/collect` |
| 3 | 定时上传任务 | `GET` / `PUT` | `/api/v1/pub/platform/schedule/uploadLog` |
| 4 | 文件服务器 | `POST` | `/XHFileServer/file/upload/{appCode}` |

文件服务器还有若干变体路径（压缩包上传、临时上传、即时上传、大文件上传），用于不同体积与场景。

### 2.1 地址是动态下发的

第 1、2 组的 base URL 来自服务端下发的配置（`getKibanaServerUrl()` / `getBigDataUrl()` 一类），APK 里只硬编码**路径**，不硬编码域名。

这一点直接决定了拦截策略：**域名黑名单必须等下发之后才知道要封谁**，而方法 hook 在调用点就能拦。

### 2.2 文件服务器的特殊地位

第 4 组同时承载：

- 头像上传
- 作业附件
- 课件资源
- 日志上传

所以「封掉它」等价于「让一批正常功能失效」。这是审计里最重要的一条判断。

## 三、本地日志的生产者

| 生产者 | 机制 | 落盘位置 |
| --- | --- | --- |
| 系统日志采集服务 | 执行 logcat 按进程过滤后持续写入 | 外部存储固定目录，文件名含包名 |
| 应用内日志管理器 | 四个写入口，按级别分流 | 同上，按应用分目录 |
| 日志服务 + 目录监听 | 监听目录变化并触发上传 | — |
| 客户端日志管理器 | 聚合各模块日志 | 私有目录 |
| 自动上报管理器 | 按策略定时上报 | — |
| 操作日志服务 | 记录用户操作序列 | 私有目录 |

**关键事实**：第一项是通过**执行系统命令**采集的，不经过应用自身的日志 API。这意味着在 Java 层 hook 应用的 log 方法，完全拦不住这一路。

## 四、七家第三方 SDK

| 类别 | 代表能力 | 风险 |
| --- | --- | --- |
| 崩溃采集 | 崩溃堆栈、设备信息、线程状态 | 高：异常即上报 |
| 性能监控 | 启动耗时、卡顿、内存 | 中 |
| 行为埋点 | 页面路径、点击事件 | 高：行为画像 |
| 语音识别 | 音频与识别结果 | 高：可能含环境音 |
| 推送 | 设备标识、在线状态 | 中 |
| 统计分析 | 会话、留存 | 中 |
| 广告/归因 | 设备指纹 | 中 |

这些 SDK 的共同特征是：**它们有自己的初始化时机、自己的队列、自己的重试策略**，且多数在 `Application.onCreate` 就启动。想「全部关掉」需要逐个处理。

## 五、禁用方案的四级优先

### 5.1 第一级：方法 hook（推荐）

在日志写入方法与上报方法的**调用点**拦截。

| 优点 | 缺点 |
| --- | --- |
| 与域名无关，不受下发影响 | 需要覆盖全部写入点 |
| 可精确到某个模块 | 新增 SDK 需补充规则 |
| 不产生副作用 | — |

这是唯一能做到「真的不产生」的一层。

### 5.2 第二级：系统开关

应用内有一个全局日志开关，存放在系统设置表里。打开后多数自有日志停止写入。

%%这个开关在系统设置的全局表里，键名可以直接改写，不需要改动应用本身。%%

| 优点 | 缺点 |
| --- | --- |
| 一行设置，覆盖面广 | 第三方 SDK 通常不看这个开关 |

### 5.3 第三级：单 SDK 粒度 hook

针对每个第三方 SDK 的初始化入口单独处理。工作量大但可控。

### 5.4 第四级：域名黑名单（仅兜底）

| 优点 | 缺点 |
| --- | --- |
| 实现最简单 | 地址动态下发，事后才知道 |
| 覆盖面直观 | 误伤正常业务（尤其文件服务器） |
| — | 客户端有重试与备用地址 |

**明确不要做**：全局封禁文件服务器域名。

## 六、漏钩：审计抓到的两个真实失误

这两个案例的教学价值高于任何结论，因为它们说明「hook 清单写错一个字，整条防线就空着」。

### 6.1 包名少一个字母

目标包名列表里写的是 `com.xh.abrstu`，真实包名是 `com.xh.abrustu`——少了 `r`。

后果：**整个包从未进入 hook 范围**，而日志与检测全部照常。由于 hook 框架不报错（它只是没匹配到），这个错误可以长期不被发现。

### 6.2 只钩了一半的命名空间

管理端使用了两组包路径做同类逻辑（`...compat.crack.*` 与 `...common.crack.*`），模块只钩了后者。另一组完全裸露。

同类问题还有 `...common.sdk.proxy.*` 与 `...system.mdm.proxy.*` 的分裂。

**教训**：hook 清单必须以「反编译树里的实际包路径」为准逐条核对，不能凭印象写。

## 七、剩下没覆盖的通道

即便把上面四级全部做好，仍有四类位置在覆盖之外：

| 通道 | 原因 |
| --- | --- |
| 原生库（`.so`）内部上报 | 不经过 Java 运行时 |
| 直接读 `/proc`、`/sys` | 不经过被 hook 的 API |
| `getprop` 系统属性查询 | 同上 |
| 独立进程/独立权限的守护进程 | 不在 hook 进程内 |

这与 [[research/postmortem]] §3.4 的分层结论一致：**应用层 hook 的天花板就在应用层。**

## 八、审计的最终判断

| 判断 | 依据 |
| --- | --- |
| 自有通道可完全覆盖 | 四组接口的调用点都在 Java 层 |
| 第三方 SDK 需逐个处理 | 各自初始化路径不同 |
| 原生与系统层无法覆盖 | 见 §7 |
| 「关掉日志」是伪目标 | 只要还有一条通道活着，结论不变 |

因此更现实的目标不是「消除日志」，而是**降低单次操作的可关联性**——这也是 [[research/postmortem]] 的核心教训。

---

## 九、这套设计的意图

从工程角度看，这些设计都是合理的：

| 设计 | 意图 |
| --- | --- |
| 多通道上报 | 容灾：一条断了还有别的 |
| 域名动态下发 | 迁移与灰度 |
| 执行系统命令采集 | 覆盖应用自身的日志盲区 |
| 第三方 SDK | 省自研成本 |

问题不在于设计，而在于**这些通道全部指向同一台设备、同一个学生**。多通道的容灾能力，在这里变成了多通道的可观测能力。

一句话概括：**容灾设计在服务端是可靠性，在客户端就是可观测性——同一套架构，两种视角。**
