# 推送长连接的协议逆向与服务发现

> 分析对象：管理端的推送长连接、内网 HTTP 微服务发现链路与其请求签名。
> 证据等级：A（反编译代码）+ B（抓包字节）。
> 配套阅读：[[research/unlocker-architecture]]（工程实现）、[[research/mdm-aidl-guide]]（下游执行者）、[[04-ipc-ztcloud]]（推送通道全貌）、[[01-network-api]]（网络栈）。

## 一、结论速览

| 问题 | 答案 |
| --- | --- |
| 帧长什么样 | `magic 0x09` + version + cmd + 变长长度 + 内容 |
| 长度怎么编 | 变长整数，首字节高 2 位存「后续字节数」，值 = 内容长度 + 3 |
| 有几个命令字 | 8 个：心跳、注册、消息、拉取、回显 + 三个回执 |
| 注册时传什么 | 文档写 7 个字符串字段，**实测只有 4 个且签名为空** |
| 请求签名怎么算 | `MD5(METHOD + URL + t + k1 + [body] + [Authorization])` |
| k1 存在哪 | 硬编码在原生库里 |
| 授权多久过期 | 7 天，凭据里内嵌序列号与日期 |
| 为什么 DNS 劫持无效 | 推送地址是**裸 IP:port**，客户端用 `matchIp` 强校验，不走 DNS |
| V2 服务发现还活着吗 | 活着，实测 200 |

一句话概括：**这条通道的设计假设是「客户端在可信网络里」，因此它把认证做成了一道可复刻的 MD5，把寻址做成了裸 IP 直连。**

## 三、帧结构

### 3.1 布局

| 偏移 | 字段 | 长度 | 说明 |
| --- | --- | --- | --- |
| 0 | magic | 1B | 固定 `0x09` |
| 1 | version | 1B | 协议版本 |
| 2 | cmd | 1B | 命令字，见 §3.3 |
| 3 | length indicator | 1 + n 字节 | 变长，n 由首字节决定 |
| 3+n | content | len | 命令相关的负载 |

### 3.2 变长长度编码

这是整个协议里最容易写错的一段。

```text
value = len(content) + 3
n     = 表示 value 需要的字节数减一（即右移 8 位的次数）
byte0 = ((n & 3) << 6) | ((value >> (8 * n)) & 0x3F)
bytei = (value >> (8 * (n - i))) & 0xFF        // i = 1..n，高位在前
```

要点：

- `value` 恒为「内容长度 + 3」，这个 3 是固定开销，不是校验；
- `byte0` 高 2 位被借用来存 `n`，低 6 位才是 `value` 的最高 6 位；
- 因此 `byte0` 之后还要跟 `n` 个字节，**总共 1 + n 字节**。

写错 `n` 会导致对端把后续内容当成新帧头，现象是「连上了但立刻断开」。

### 3.3 命令字

| 值 | 名称 | 方向 | 说明 |
| --- | --- | --- | --- |
| `0x01` | `HEART_BEAT` | C→S | 心跳，实测 30 秒 |
| `0x02` | `AUTHORIZATION` | C→S | 注册/授权 |
| `0x03` | `MESSAGE` | S→C | 业务消息下发 |
| `0x05` | `PULL` | C→S | 主动拉取 |
| `0x32` | `ECHO` | 双向 | 探活/回显 |
| `0x82` | `AUTH_FB` | S→C | 注册回执 |
| `0x83` | `MESSAGE_FB` | C→S | 消息回执 |
| `0x8B` | `ERROR_FB` | S→C | 错误回执 |

### 3.4 注册帧的真实内容

文档与实现不一致，这里两版并存记录：

| 版本 | 字段 |
| --- | --- |
| 协议文档描述 | 7 个「1 字节长度 + UTF-8 字符串」：`accessKey`、`deviceId`、`clientId`、`signature`、`token`、`uid`、`tags` |
| **实测抓包** | **4 个**：`accessKey`、`deviceId`、`signature`（**空字符串**）、`clientId` |

结论：**签名字段存在但为空，实际不参与认证。** 服务端只按 `accessKey + clientId` 认设备。

而这两个值的来源是本地配置文件（`sec.ini`）里的 `uv` 与 `randomStr` 字段——%%凭据就落在应用私有目录的这个 ini 文件里，字段名与文件路径固定，不需要再逆向%%。

### 3.5 消息帧内容

```text
mode    1B    消息模式
count   2B    条目数
entries       每条：
  msgId        8B    有符号，序号
  contentLen   4B    有符号，上限 10MB
  content      nB    UTF-8 JSON
```

消息实体字段（除 `style` 全为字符串）：

| 字段 | 说明 |
| --- | --- |
| `appId` | 目标应用 |
| `subAppId` | 子应用；路由前置条件为 `appId == subAppId` |
| `clientId` | 目标客户端 |
| `msgId` | 消息序号 |
| `msgType` | 类型 |
| `payload` | 业务负载 |
| `style` | 整型样式 |
| `subMsgType` | 二级路由键 |
| `userId` | 用户 |

**回执语义（关键）**：接收方**无条件**发回执；发送方**在回执成功后才分发**。这意味着「收到回执」≠「业务已执行」，回执早于分发。这条与 [[research/unlocker-methodology]] §4.5 的判定完全对应。

### 3.6 subMsgType 路由表

| subMsgType | 去向 |
| --- | --- |
| `assist-notify` | 远程协助受理 |
| `control-service` | 管控指令下发 |
| `app-upgrade` | 应用升级 |
| `app-upgrade-prepare` | 升级预处理 |
| `app-syncMessage` | 消息同步 |
| `app-notification` | 通知栏推送 |

## 四、请求签名

### 4.1 算法

```text
sign = MD5( METHOD + URL + t + k1 + [body] + [Authorization] )
```

| 参数 | 说明 |
| --- | --- |
| `METHOD` | 大写，如 `GET`/`POST` |
| `URL` | 完整路径，含 query |
| `t` | 毫秒时间戳 |
| `k1` | 硬编码密钥，位于原生库 `libxhcore.so` |
| `body` | 有请求体时拼接 |
| `Authorization` | 有该头时拼接 |

### 4.2 k1 的取法

k1 不是常量字符串，而是运行时从原生库解出的一段字节。取它的方式有两种：

- 在原生库初始化后从内存/寄存器落点读取；
- 直接调用其导出函数。

两者都需要能在目标进程或同架构环境里执行代码，这也是为什么纯静态阅读拿不到它。

### 4.3 签名的实际作用

它挡的是**外部人直接调接口**，不挡**已在本机运行的应用**——后者可以按同样算法自己算。

## 五、授权与凭据

### 5.1 七天上限

抓到的授权凭据是一个 Base64 串，解开后是「序列号 + 日期」的明文拼接，例如：

```text
<序列号>20261114
```

与同时抓到的令牌过期时间（2026-11-14 17:20）吻合。结论：**授权以 7 天为滚动窗口，凭据在客户端本地生成，不做服务端吊销**。

### 5.2 这意味着什么

- 凭据是可离线生成的，不需要每次联网换；
- 序列号在凭据里是明文的；
- 「过期」只是客户端不再发送，而不是服务端拒绝。

## 六、服务发现与网关寻址

### 6.1 两代服务发现

| 版本 | 接口 | 状态 |
| --- | --- | --- |
| V1 | `POST http://ms.yunzuoye.net/XhServerMg/GetXsList`，表单 `K=<JSON>&Z=0` | 已退役 |
| V2 | `POST /api/v2/pub/microServer/list/` | **实测 200，活着** |

两代接口返回的都是「微服务名 → 地址列表」的映射。

### 6.2 服务类型码

| 码 | 服务 |
| --- | --- |
| `SA106003` | LAUNCHER |
| `SB103015` | CONTROL |

### 6.3 UrlCache 机制

| 概念 | 说明 |
| --- | --- |
| `position` | 初始为 `-1`，表示「尚未选中任何地址」 |
| 首次取址 | `getAddressList(类型码)[0]` |
| 地址来源优先级 | 登录响应的 `microAddressDTOList` > 本地默认表 |
| 本地默认表 | 仅一条，HTTPS 域名形式 |
| 失败处理 | `nextHttpUrl()` 轮换到下一条 |

`microAddressDTOList` 在实测登录响应里是 `null`，所以实际总是落到本地默认表。这是「伪造登录响应注入地址表」这条思路的立足点（见 [[research/attack-chain]]）。

### 6.4 为什么自签证书方案不可行

客户端的 TLS 实现严格拒绝自签证书，且不信任用户安装的 CA（受 `targetSdk` 限制）。三条证据叠加：

1. 信任管理器只接受系统根证书链；
2. 主机名校验有独立实现，不复用系统默认；
3. 实验性自签拦截在握手阶段即失败，客户端直接断开，不进入应用层重试。

结论：**在应用层做 TLS 中间人这条路走不通**，只能从「让客户端自己选一个明文地址」入手。

## 七、推送地址为什么不能用 DNS 劫持

推送地址是**裸 IP + 端口**，客户端在连接前做 `matchIp` 强校验——比对目标 IP 是否在预期集合内。DNS 完全不在链路上。

因此接管必须发生在**网络层**：让设备真的连到我们控制的 IP。两种做法：

| 方案 | 效果 |
| --- | --- |
| 在本机网卡上加 /32 副地址 | 会让承载热点的网卡重新协商，热点自毁 |
| 挂在 Loopback 上并开启弱主机收发 | 热点稳定，接管生效 |

第二种做法需要开启弱主机模型（`weakhostreceive` / `weakhostsend`），否则内核认为该 IP 不属于任何可达接口，直接丢弃。

## 八、工程实践：三个 Windows 网络坑

### 8.1 动态端口区与保留区重叠

监听时报 `WSAEACCES (10013)`，原因不是权限，而是目标端口落在了系统动态端口区与 Hyper-V 保留区的重叠段。

修复：把动态端口起点后移，避开保留段。

```text
netsh int ipv4 set dynamicport tcp start=30000 numberofports=18000
```

修复后连续 10 次监听全部成功。

### 8.2 后台监听进程的套接字被回收

以普通方式启动的后台进程在会话结束时套接字被系统回收，表现为「刚起来就断」。需要用脱离父进程的方式启动（`Start-Process` 一类），否则进程存活但监听失效。

### 8.3 热点网卡加副地址导致热点自毁

见 §7。这是三个坑里唯一一个「看起来成功、实际把自己网络搞没了」的，排查耗时最长——因为现象是设备离线，而不是报错。

## 九、离线验证

复刻编解码之后可以先离线跑通，再上现场：

| 验证项 | 判据 |
| --- | --- |
| 编码器自洽 | 自己编的帧能被自己的解码器读回，长度字段完全一致 |
| 与真实帧对齐 | 逐字节比对真实捕获帧，差异能逐项解释（时间戳/序号/随机数） |
| 回执关联 | 用 `msgId` 确认「这一帧」被处理，而不是「某一帧」 |
| 业务副作用 | 单独验证，不把回执当副作用 |

## 十、这套协议暴露了什么

把技术细节抽掉，这套设计有三处结构性假设：

| 假设 | 现实 |
| --- | --- |
| 客户端在可信网络内 | 热点、共享网络、校园网全都是可被二三层旁路的 |
| 认证能挡住伪造 | 签名可复刻，且实测根本没校验 |
| 凭据短期有效即安全 | 凭据本地生成，无吊销 |

对应的结论不是「这套协议很糟」，而是：**它把一个面向受管内网的设计，直接部署到了学生的个人设备上，而两者的威胁模型完全不同。**

一句话概括：**一条以裸 IP 寻址、以可复刻 MD5 为门、以本地生成凭据为凭的通道，它的安全性来自「没人会去看」，而不是来自设计。**
