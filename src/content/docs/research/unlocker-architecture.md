# Unlocker 工程的架构与服务发现

> 分析对象：`O-XueHai-Unlocker` 工程（公开版）。
> 路径均相对工程根目录。
> 配套阅读：[[research/push-channel-reverse]]（协议逆向）、[[research/mdm-aidl-guide]]（下游执行）、[[research/attack-chain]]（Private 版的完整链路）。

## 一、结论速览

| 问题 | 答案 |
| --- | --- |
| 工程分几层 | 四层：协议层、服务发现层、设备端层、执行层 |
| 最难的部分 | 不是协议，是**字节级完全一致**——差一个字节就断开 |
| 唯一没过去的墙 | TLS 信任。客户端严格拒绝自签证书，且不信任用户 CA |
| 那还有什么路 | 伪造登录响应，往 `microAddressDTOList` 里注入自己的地址 |
| 为什么要分层 | 每一层都能独立验证，出错时能快速定位到哪一层 |
| 方案对版本敏感吗 | 极度敏感。事务号、字段顺序、方法签名都随版本变动 |

一句话概括：**协议逆向是一次性的智力活，工程复刻是持续的精度活，而最后卡住的往往是设计上根本没打算让你碰的那一层。**

---

## 二、四层组件

| 层 | 职责 | 典型产物 |
| --- | --- | --- |
| 协议层 | 帧编解码、命令字分发 | 编码器/解码器、帧构造工具 |
| 服务发现层 | 找服务、选地址、处理轮换 | 地址表注入器、探测脚本 |
| 设备端层 | 在目标设备上跑的最小执行体 | 载荷 APK |
| 执行层 | 把上层指令落到具体动作 | 命令执行器、安装器、文件操作 |

分层的好处：协议层可以离线验证（编解码往返），服务发现层可以半离线验证（接口探测），只有后两层必须上真机。

---

## 三、协议层实现要点

### 3.1 长度编码是最容易错的一处

| 错误 | 现象 |
| --- | --- |
| `n` 算错 | 对端把后续内容当新帧头，连接立刻断 |
| `+3` 的固定开销漏掉 | 长度差 3，越界读 |
| 高位字节序写反 | 小负载正常、大负载断，最难查 |

**验证方法**：写一组从 0 到 10MB 的填充负载，编解码往返，逐字节比对。

### 3.2 帧构造工具

工程里有一个独立的帧构造工具，用于在不启动完整客户端的情况下产出可发送的帧。它的价值在于：可以把「协议是否正确」与「网络是否通」两个问题分开验证。

### 3.3 消息体上限

单条消息内容上限 10MB（4 字节有符号长度字段）。超过时客户端直接拒绝，不报错。

## 四、服务发现层

### 4.1 两个候选源

客户端找服务地址时按优先级取值：

| 优先级 | 来源 | 现实 |
| --- | --- | --- |
| 1 | 登录响应的 `microAddressDTOList` | 实测为 `null` |
| 2 | 构建期内置的默认地址表 | 一条 HTTPS 域名 |

第 1 项为空使第 2 项成为实际生效路径。**这也是「伪造登录响应」思路的立足点：既然客户端信任登录响应里的地址表，那就让登录响应给出我们的地址。**

### 4.2 地址表的结构

| 字段 | 说明 |
| --- | --- |
| 服务类型码 | 标识这是给哪个微服务用的地址 |
| 地址 | 字符串，协议部分可为 `http` |
| 权重/顺序 | 决定 `position` 的推进顺序 |

关键点：**协议字段允许 `http`**。客户端不会强制升级到 HTTPS。这是整条路径上唯一一个不需要碰 TLS 的缺口。

### 4.3 令牌失效的全局拦截

客户端有一个全局拦截器：任何响应只要带「令牌失效」状态，就会触发强制重新登录。

这是排查「伪造之后没有反应」时必须先排除的一项——很多看起来「方案无效」的情况，实际上是伪造的响应被这个拦截器吞掉了，业务逻辑根本没走到。

## 五、设备端层与执行层

### 5.1 载荷的最小条件

| 条件 | 原因 |
| --- | --- |
| 包名必须是系统内置应用之一 | 只有内置包能覆盖升级，且能命中零点击自启的硬编码目标 |
| 签名必须与已装包一致或不冲突 | 否则安装失败 |
| `versionCode` 必须递增 | 否则上层跳过安装 |
| 不能自定义 `Application` 子类 | 特定环境下会崩 |
| 网络操作不能放主线程 | 否则直接抛异常退出 |

### 5.2 执行层的两类入口

| 入口 | 特点 |
| --- | --- |
| 静默安装（MDM） | 无用户交互，无签名校验，但有版本与签名两个前置条件 |
| 零点击自启（固定广播/显式 intent） | 不需要用户点，但对包状态敏感（stopped 态解析不到） |

## 六、为什么自签证书方案走不通

这是整条路径上唯一一道真正过不去的墙，三条独立证据：

| # | 证据 | 结论 |
| --- | --- | --- |
| 1 | 信任管理器只接受系统根证书链 | 用户安装的 CA 不被采信 |
| 2 | 主机名校验有独立实现 | 替换系统校验器无效 |
| 3 | 实验性自签拦截在握手阶段即失败 | 客户端直接断开，不进入应用层重试 |

第 3 条是决定性的：不是「证书被警告后可以继续」，而是**连接根本没有建立**。

因此结论是：**不要试图做 TLS 中间人，去让客户端自己选一个明文地址。** 这也是 §4.1 那条路存在的全部理由。

## 七、与主线的关系

这个工程对应的是「协议在线上真实长什么样」。它和静态分析的关系是：

| | 静态分析 | 本工程 |
| --- | --- | --- |
| 回答 | 代码允许什么 | 线上实际是什么 |
| 证据 | 反编译源码 | 抓包字节 + 现场行为 |
| 局限 | 看不到运行时分支 | 看不到未触发的路径 |

两者交叉之后才能得出「这个结论可信」的判断，这也是 [[research/unlocker-methodology]] §3.5 的要求。

## 八、工程层面的三条经验

### 8.1 先把「不可能」证死

自签证书这一项花了大量时间才确认无解。回头看，**尽早做「证伪实验」比继续加功能更有价值**——一个被彻底排除的方向，比十个半通不通的方向更省时间。

### 8.2 每一层都要有独立判据

| 层 | 判据 |
| --- | --- |
| 协议层 | 编解码往返逐字节一致 |
| 服务发现层 | 接口探测返回预期结构 |
| 设备端层 | 进程存活 + 拿到 `uid` |
| 执行层 | 具体副作用可观测（文件出现、应用被装） |

没有独立判据，就会出现「全都试了、不知道哪一步坏了」的局面。

### 8.3 版本敏感性要写在最前面

事务号、字段顺序、方法签名、包名、常量——全部随版本变动。任何方案的第一页都应该写清楚它针对哪个版本，否则三个月后连自己都无法复现。

---

一句话概括：**协议可以复刻，工程可以打磨，但「客户端信不信你的证书」这件事，不是靠努力能解决的。**
