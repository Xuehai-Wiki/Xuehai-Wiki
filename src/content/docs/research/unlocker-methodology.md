# 逆向研究的证据分级与验证方法

> 分析对象：一批针对商业终端管理体系的长期逆向研究的元方法论。
> 本文不含任何具体目标的技术细节，可直接阅读。
> 配套阅读：[[research]]（研究资料索引）、[[deep-dive-into-ztp]]（静态分析主线）。

## 一、结论速览

| 问题 | 答案 |
| --- | --- |
| 分几级证据 | 三级：A 代码级、B 字节级、C 行为级，另有「不予采用」一类 |
| 为什么日志不算证据 | 日志有多个开关和远程上报通道，缺失不能证明未执行，存在也不能证明已执行 |
| 一个结论要几处确认 | 至少两处独立代码，或一处代码 + 一处字节 |
| 回执成功说明什么 | 只说明解析成功，不说明业务已执行 |
| 单次现象能不能归因 | 不能。必须建基线、单变量、覆盖最长延时、重复至少两次 |
| 假设怎么写 | 必须附可证伪的判据，否则不算结论 |

一句话概括：**证据分级解决「信不信」，验证流程解决「凭什么信」，两者都不做就只是一篇推测。**

## 二、三级证据体系

### 2.1 A 级：代码级

结论直接由反编译/反汇编源码得出，且能定位到具体文件与行号。

判定要求：

- 给出文件路径与行号，例如 `SceneControlStatus.smali:884`；
- 给出触发该分支的**判定表达式**，而不只是「这里有判断」；
- 对每个 `if` 分支，记录判定表达式与默认值，并说明在何种设备状态下会通过。

这是唯一可以单独支撑「必然发生」结论的级别。

### 2.2 B 级：字节级

结论由实际收发的字节流、文件内容或二进制结构得出，可复现、可逐字节比对。

适用范围：

- 抓到的协议帧（含长度编码与校验）；
- 落盘文件的字段值（数据库行、ini 键值）；
- 二进制的结构特征（导入表、GOT 偏移、CRC）。

B 级的特点是**不可辩驳**：字节就摆在那里。但它只证明「发生过一次」，不能直接外推到「每次都会」。要外推，必须叠加 A 级代码解释。

### 2.3 C 级：行为级

结论由可观察的系统行为得出：界面变化、进程存亡、文件出现或消失、网络包的有无。

C 级是可接受的，但必须满足完整归因流程（见 §5）。单独一条 C 级观察的措辞只能是「观测到」，不能是「导致」。

### 2.4 不予采用：运行日志与界面提示

这一类被明确排除在证据之外，理由是两个方向都不成立：

| 方向 | 为什么不可靠 |
| --- | --- |
| 日志缺失 ⇒ 逻辑未执行 | 日志有多渠道开关，还有远程上报；开关关闭或上报失败时逻辑照常执行 |
| 日志存在 ⇒ 逻辑已执行 | 日志点常写在分支入口，实际业务可能在其后异常退出 |

界面提示同理：同一句文案可能来自本地判定、服务端下发的状态、或某个 SDK 的兜底。**文案是结果，不是原因**，只能作为定位线索，不能作为结论依据。

第三方转述（论坛帖、群聊截图）同理，只能作为线索。

## 三、逆向流程五步

### 3.1 定位包与组件

先确定目标进程、包名与入口组件，再决定反编译范围。多包体系（主应用 + 管理端 + 服务端 SDK + 原生库）要分别建树，不要混在一棵目录里。

### 3.2 反编译出可检索的树

`apktool` 取资源与清单，`jadx` 取 Java 语义，必要时对关键 `.so` 做反汇编。三者并存，互相印证。

**检索必须用脚本，不能用 shell 通配递归。** 反编译树动辄十万文件，shell glob 会因参数长度与编码问题静默漏文件；脚本要带容错读取（跳过非法 UTF-8）。

### 3.3 调用链回溯

从可观测的现象反推：
`现象 → 触发它的方法 → 调用方 → 再上一层`，直到到达外部输入（网络、文件、IPC、广播）。

每一跳都要记 `文件:行号`，链条断在任何一跳都说明还有未解释的部分。

### 3.4 门禁枚举

把链路上所有判定条件列成表：

| 门禁 | 判定表达式 | 默认值 | 通过所需设备状态 |
| --- | --- | --- | --- |

这一步是整个流程里最容易被跳过、也最容易导致「方案看起来可行但实际不动」的一步。经验上，一条链路上 70% 的失败都发生在这里，而不是在技术实现上。

### 3.5 交叉验证

同一事实至少要有两处独立来源：

- 两处互不相关的代码；或
- 一处代码 + 一处字节。

若做不到，就在结论里明确降级为「假设」。

## 四、协议验证五步

### 4.1 先写编码器

在发送任何东西之前，先写出把结构体序列化成字节的函数。手搓十六进制字符串的方式无法迭代。

### 4.2 离线回读

用自己的解码器读回自己编出的帧，确认长度字段、校验字段、变长编码自洽。这一步能吃掉大部分低级错误。

### 4.3 与线上真实帧逐字节对齐

拿一份真实捕获的帧做基准，逐字节比较。差异必须能逐项解释：哪个字段是时间戳、哪个是序号、哪个是随机数。

### 4.4 现场发送

只有在 4.3 通过后才上真机。发送时保留完整十六进制转储与时间戳。

### 4.5 回执关联

用回执里的标识（消息 ID、事务号）确认「发出去的这一帧」被处理了，而不是「某一帧」被处理了。

**这里有个关键判定**：回执只是解析成功的证据，不是业务已执行的证据。回执通常早于业务分发，且回执发送失败会阻断分发。所以「收到回执」与「副作用发生」是两个必须分别验证的命题。

## 五、副作用归因五步

当观察到「做了 X 之后出现了 Y」时，按以下顺序处理：

1. **建基线**：不做任何操作，观察 Y 是否本来就会发生。很多「副作用」是系统周期性行为的巧合。
2. **单变量**：一次只改一个条件。同时改三个变量得到的差异无法归因。
3. **窗口覆盖最长延时**：观察窗口必须长于链路上最长的定时器。已知存在 120 秒级、数分钟级同步循环时，30 秒窗口毫无意义。
4. **重复至少两次**：一次成功可能是环境残留。
5. **无差异则判未观测**：如果多次实验都得不到可区分差异，结论应写成「未观测到该副作用」，而不是「该副作用不存在」。

## 六、现场环境四条

| 条件 | 说明 |
| --- | --- |
| 同广播域 + 链路层可达 | 跨网段时二层劫持类手段全部失效，且很难从现象上看出来 |
| 需提权否则只见广播 | 非提权抓包只能看到广播/组播，会得出「没有单播流量」的错误结论 |
| 过滤表达式尽量宽 | 先按 `ip` 全收，再在本地筛；收窄 BPF 会漏掉真正要看的流量 |
| 字节序号必须同一进程维护 | 序列号跨进程重置会导致对端判定为乱序而丢包，现象上与「没发出去」难以区分 |

---

## 七、结论表述四条

1. **已确认**：A 级或 B 级支撑，可直接陈述。
2. **已观测**：C 级支撑，必须写明「在什么条件下观测到」。
3. **假设**：必须附可证伪判据，例如「若假设成立，则 X 条件下应出现 Y；否则不出现」。
4. **不计入链路**：依赖人工操作的步骤（点一下、手动输入一次）必须显式标注，不能算作自动化能力。

## 八、这套方法实际挡掉了什么

| 常见误判 | 被哪一条挡住 |
| --- | --- |
| 「日志里没有这条，说明这个分支没走」 | §2.4 |
| 「发了帧收到回执，说明命令执行了」 | §4.5 |
| 「改完就崩了，所以是这次改动导致的」 | §5.1、§5.2 |
| 「试了一次就成功了」 | §5.4 |
| 「代码里有这个入口，所以能利用」 | §3.4 |
| 「文档这么写的」 | §3.5 |

一句话概括：**方法论的唯一作用，是让「我以为」变成「我能证明」，或者干脆承认「我不知道」。**
